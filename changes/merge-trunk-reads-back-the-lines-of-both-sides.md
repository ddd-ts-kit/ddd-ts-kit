**`ddd-ts-kit merge-trunk` reads back the lines of both sides it keeps in a generated region, and merges the region declaration by declaration when those lines would mix the two sides.**

What you see. Your branch and the trunk conflict inside a generated region of a TypeScript, JavaScript or Prisma file (the tables of a context, the handlers of a module). `merge-trunk` keeps the lines of both sides of each conflict, and until now it committed the region whenever its brackets paired, exit 0, `generated registry: the lines of both sides kept`. After a hand edit inside the region that could be wrong: your branch adds a column above `version` in the table of the orders and stores an aggregate below it, the trunk adds a column at the same place, and the column of the trunk was written in the new table (on Knex the project still type-checked). From this version:

- a column, an argument or a statement of one side is no longer written inside a table, a function or a call of the other;
- a table one side removed and the other only moved does not come back, and a table is not written twice;
- a comment stays above the declaration it was written above, and a constant a side added under a table stays below that table when the other side moved it;
- a chain or a call written on several lines keeps its lines when the other side added one that shares some of them.

Three things can happen where the two sides conflict in such a region.

1. Nothing changes: the same file and the same report line as before, whenever the lines of both sides hold each declaration of the two sides whole and once, none above one it reads; the order of the lines of both sides is otherwise kept. Everything the generators write alone is in this case.
2. The region is merged declaration by declaration, and the report says `generated registry: the declarations of both sides kept, each one whole`: the table one side added is kept whole, the one a side changed or removed while the other left it alone follows that side, the declarations stand in the order of the side that alone changed it, and what a side alone added stands after the declaration it follows on that side.
3. The merge stops, exit 1, on one hunk per declaration the two sides do not agree on, the rest of the region being merged. The hunk holds each version of the declaration whole: ``the two sides do not agree on `orders` in the region `tables`: for each, write the one declaration that keeps the intent of both, whole, or remove it.`` Write the declaration once with what both sides meant, `git add` the file, then `npx ddd-ts-kit merge-trunk --continue`. This is what the example above now gives: one hunk on the table of the orders, with the version of each side, and the new table whole below it. The same holds for a table one side removed and the other changed. When a region has to be merged this way and each side set its declarations in an order of its own, nothing is written in the region and the hunks git wrote stay, as since 0.113.1.

When. Each conflicted region whose three sides the kit reads with certainty is read back, declaration by declaration, a comment belonging to the declaration it stands above. The lines of both sides are kept when the region they give holds, for each declaration, what the three sides merge into: the one a side added, changed or removed while the other left it as the base holds it, the one both wrote alike, and for one both changed the lines the kit keeps of that declaration merged alone (what git merges of its three versions and the lines of both sides of each conflict left). The order of the lines of both sides is kept, with one rule: a declaration that reads another one stands below it, as on the side that wrote it. The lines are not kept when a declaration names, in its code, one that stands below it in the region they give while every side that holds the two sets it above; a function a side wrote above the one it calls is as that side wrote it. A comment both sides wrote, word for word, above the declaration each added is kept once, above the first, as before. Blank lines are not compared: the lines of both sides keep one of each run, so a comment a side set apart from its declaration by a blank line stands right above it. In the `imports` region the lines are kept when they bring the same names from the same modules as the statements of both sides.

Three stops are new.

- A rename against a change, where the lines of both sides were right: one side gives a table another name by hand and the other side adds a column to it by hand (you rename `payments` to `invoices`, the trunk adds `paidAt` to `payments`). The kit cannot tell a declaration given another name from one replaced by another, so it leaves the table the trunk changed as one hunk, the rest of the region merged, and says so: `If a declaration of the side that removed it is this one under another name, write the change there and remove the hunk.`
- A declaration one side removed and the other started to read: one side removed a declaration the other left alone, and that other side wrote or changed a declaration that now reads it. Nothing is written in the region and the hunks git wrote stay: ``the region `tables` holds a declaration one side removed and that a declaration the other side wrote reads``; keep the one removed, or write the other without it.
- A declaration that would stand above one it reads: when the region merged declaration by declaration would set it there while the sides set it below, nothing is written in the region and the hunks git wrote stay: ``the region `tables` holds a declaration that would stand above one it reads once the two sides are merged``; write the region in the order that holds for both.

Limits.

- A merge git settles with no conflict is never read back: where git itself sets a column in the wrong table, nothing reports it.
- A region the kit does not read with certainty is merged by lines, as before, whatever its conflicts look like: one that holds a regular expression, a constant and a type or an interface of one name, the signatures of one function, one statement written twice, a region written inside it, or that a side does not hold once. So is a region in which a side holds lines that end no statement (entries of a list, statements written without `;`), whether the two sides differ on them or not.
- Two edits of one line are both kept, as before: each side adds an argument to a call written on one line, and the call stands twice.
- Statements that declare no name (a call, a registration) have no name to be paired by: one a side removed and the other changed is kept as changed, and a comment a side wrote above one may stay above its neighbour.
- Inside one declaration both sides changed, the lines of both sides are kept unless a conflict there breaks a statement written on several lines. The kit sees such a statement when it holds a bracket open from one line to the next; when a line starts with `|`, `&`, `?`, `:`, `.`, `+`, `-`, `*`, `/`, `=`, `satisfies` or `as` (three dots start an entry of their own); when a line ends with `=`, `+`, `-`, `*`, `|`, `&`, `?`, `:`, `.` or `=>`; when it is a block comment; or when a line starts with `@`, does not end with `;` and has a line under it. In a schema of Prisma, only the bracket and the block comment. Another way of writing a statement on several lines is not seen.
- Inside one declaration both sides changed, the lines of a conflict stand ours first, then the trunk's, as before: a line one side added under a line the other changed can stand above it, and a line one side removed and the other changed is kept as changed.
- A declaration both sides changed, one of them by setting a comment above it apart by a blank line, can be left as one hunk where the lines of both sides were right: git aligns the conflicts of the file otherwise than those of the declaration merged alone, and the kit then does not read the two as the same (4 in 12000 conflicts measured).
- Two import statements that name one module, one wrapped on several lines and the other not, are both kept, and a name can then be imported twice, as before.
- What a declaration reads is found by name, in its code, comments and strings left out, and no scope is read. A read is the name as a whole word: in an expression, in a type (`typeof orders`), spread (`...orders`), as a shorthand property (`{ orders }`). A member of another value is not a read (`other.orders`, `other?.orders`), nor a member the code declares under that name: a key (`orders: 1`), a member of an interface or of a type, a method or an accessor, a field of a class, a member of an enum. A declaration that binds the name itself is taken to read no outer declaration of that name at all: a parameter, with or without a type or a default, the parameter of an arrow (`orders =>`), a local `const`, `let`, `var`, `function` or `class`, a destructured binding, a catch clause, a label, an alias of an import or an export. A real read written beside such a binding is therefore not seen, and the region is merged as before this change.
