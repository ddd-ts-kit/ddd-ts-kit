**Two contexts may hold a table of the same name on Drizzle and on TypeORM.** `ddd-ts-kit generate read-model billing InvoiceSummaries` then `generate read-model shipping InvoiceSummaries`, or two aggregates of one name stored in two contexts, or the identity preset beside a context that holds `accounts`, wrote a schema index (`src/platform/database/schema.ts`) that named the same constant twice: the project did not compile, and on Drizzle the migration `db:generate` wrote, like the test database, left out the tables of the second context without a word. The two tables never met in the database, each being in the schema of its context, and they still do not; Knex and Prisma were not concerned. The index now settles the name: the context that held it first keeps it, and the second is listed under a name that carries its context, `export { invoiceSummaries as shippingInvoiceSummaries } from` on Drizzle beside `export { invoiceSummaries } from` for the first; on TypeORM `generate` imports the second table it creates as `import { invoiceSummaries as shippingInvoiceSummaries }`, and after a merge that leaves one name imported twice a person writes that alias. The tables file of a context, its stores and its repositories keep the name of the table. The same holds for a table that bears the name of one the index declares itself, `jobs`, `outbox`, `processes`: on Drizzle the aggregate `Job` of a context compiled, and its table was never created, the constant of the index hiding it; it is now listed as `billingJobs`. The name the second table takes is one nothing holds: where `shippingOrders` is the table `shipping_orders` of a context, or `shippingSchema` the schema constant of the context, it is `shippingContextOrders`, then `shippingOrders2`.

What is settled, on Drizzle. A name two tables files of contexts export, each its own table, or one the index declares itself: each command that writes the index (`generate`, `init --force`, `merge-trunk`) writes the lines by name the whole index lacks, not only those of the context it works for, in the `// ddd-ts-kit:schemas` region, one name a line. What is compared is a symbol, the file that declares it and its name, each file by the path it is read at, a context laid out in modules (its tables file in `shared/`) as a flat one: two tables files that re-export one table of the shared kernel hold one symbol, whether one names the file through the alias of the project and the other by a relative path, which `export *` brings as before, and nothing is written nor said. Where the index gives a shared name to nothing yet, the context it re-exports first keeps it; a generator leaves it to the other context only for the name its command brings, and `merge-trunk` gives it to the table the trunk exports under it when the kit settles it, whatever the order of the index and whatever the layout of a context on either side: each side is read as its commit lays its contexts out, flat or in modules, so a table that moved to `shared/` on one side is the same table on the other, and the merge says nothing of it unless a line still names the old place. A name that has a value in a tables file, a table beside the type of its rows (`export const invoices` and `export type invoices`), an enum and the type of its values, a class and an interface, is exported from it with a plain `export { ... }` line, which carries the type too; `export type { ... }` is written only for a name that is a type and no value in that file. `default` is never settled. After the lines are written the kit reads the index again: every value of every file it re-exports whole must be exported as a value under a name, or the lines are taken back. The sentence `lists the name ... as ...` is printed for each line that was written.

What is only said. `generate` and `init --force` compare what the index gave before the command with what it gives after: on Drizzle the names it exports as values and the table each one exports (a name it exports as a type only is not compared), on TypeORM the entities `entities` lists, as far as the kit reads them. A value a file exports by name, which the index exported before under that name or another (`export *`, `export { a } from`, `export { a as b } from`) and would export under it no more, an entity listed no more, or a name that exported one table and would export another, everything the index re-exports read with certainty, leaves the index as it stood before the command: the comparison is made once, when every generator of the command has run, on the state the command ends in. The index is listed under `left` and in `skipped` of the report, never in `updated`, and the command exits 3. One note names every name concerned, with the file that gives it, and says what would have been lost or moved: `` the name `archived`, which 'src/legacy/tables.ts' gives the index, would be exported by no line after it (a table still exported under another name is not seen: the kit compares names) ``, the file being the one the line of the index names, or the package, `` `orders`, which named the `orders` of '<a>', would name the `orders` of '<b>' ``; `generate` gives the lines it wrote, to write by hand, when it wrote some, and ends with what leaving them out costs when the `export *` line of a context is among them (its tables are listed nowhere, no migration will create them); `init --force` gives none: the line that keeps the name, or what keeps several, belongs in the `// ddd-ts-kit:schemas` region, which the rewrite keeps, and until it is moved there every `init --force` leaves the index as it stood. A table `generate --force` drops from a tables file it writes again whole is said in a note, on Drizzle and on TypeORM (where the index, which still imports it, does not compile), and the command exits as it would without it: the index is not left for that. A tables file that is a symbolic link gets no such note: the kit does not read it. A name that did not compile before, two `export *` bringing it, exported nothing: settling it is no such change. `generate` refuses, before it writes anything, a table whose name the tables file of the context already exports from another file. `ddd-ts-kit init --force` writes the index again from its template, which drops what a team wrote outside the `// ddd-ts-kit:` regions; it leaves the index as it stood on disk, with one note, when that would lose a name the index exports, or give it to another table, everything the index re-exports read with certainty, and when the part outside the regions holds something it does not read with certainty (on Drizzle an `export` it does not answer for or a module re-exported whole it does not follow; on TypeORM an entry of `entities` the rewritten list lacks, unless it is a constant the index builds by calling a function imported from a package of the kit: that one is taken for a line of a template and goes with the rewrite, as before) and the rewrite would drop a line written there. Apart from that rewrite, no command removes a line of the Drizzle index: the line of a table that is gone is a compile error to fix by hand. On TypeORM no command removes or renames an import of the index: `generate` only adds the import of the table it creates, under a name of its own when its name is taken.

On Drizzle, `ddd-ts-kit merge-trunk` settles the names the two sides share between tables files of contexts, in lines of the shape the kit writes, and says so under `automatic:`, in a dry run too, which reads the files the merge reads, each file the merge writes as it writes it, a file left to a person as the text it is handed; a configuration both sides changed, conflicted in the tree the dry run reads, is read as a resolution keeping the contexts of both sides would read it, the branch's with the contexts of both sides; a dry run that cannot say what the merge would settle, the configuration still unread or the files of the tree not read, says so only when the two sides give one name to two tables, and exits as it would without it. The dry run writes nothing, not even a temporary copy of the tree. On Drizzle, a line or an import of the merged index that names the place a side held a context's tables file at, which the merged tree no longer holds because the other side moved the file (`context-layout` laying the context out in modules), is not written again: the index is left as the merge wrote it, a compile error as before, and the report says each such line, in the dry run too: `` `export { orders } from '...'` names '<old place>', which the merged tree no longer holds: billing's tables file is now '<new place>'; write that path in the line``. While such a line is there, the kit writes no name nor any other line of that merge, and says it once. A file counts as moved only when the merged tree holds no file at its old place. When it holds both, one side having laid the context out in modules while the other stored a table flat, the context has two tables files, and on Drizzle what follows applies; a file counts as a tables file only when it declares a value of its own, so a flat file that only re-exports the one of `shared/`, or an empty one, is none. When the two files declare no name in common, the merge goes on as any merge. When they declare one (the schema of the context first), the kit writes no name, nor any other line of that merge, and says it once: it names the two files and the names both declare, and says what must hold once a person made them one file, the one of `shared/`: every table of the flat file there, on the schema it declares; for a table name both declare, the one of the two files the trunk's index exports it from, under that name or another, keeps it (the sentence names that file and the name the trunk gives it) and the other takes a new name in every file that imports it; a schema constant both declare is kept once, the tables of the flat file built on the one of `shared/`; the flat file and the `export *` line that names it gone, every other import and line of the index pointed at `shared/`; then a commit and `npx ddd-ts-kit init --force`. The report still names each table hidden and each name moved, as in any merge. When the merge stops on a conflict, the sentences about the names come at `--continue`, once; the dry run gives them in advance. A name the trunk exports keeps naming the table of the trunk when the line that gave it to another table on the branch is one the kit wrote, one name a line; any other shape (a line by hand with several names, a module that is no tables file of a context) is not repaired. Whatever it wrote, the report then says, the dry run as the merge: each table a side had within reach, still in the merged tree, that the merged index exports under no name, with its file and the name that hides it; and each name of the trunk or of the branch that names another table after the merge, when the table it named is still re-exported whole (`export *`) by the merged index. When the kit does not read a side or the merged index with certainty, cannot write the index, or would give a name of the trunk to another table, it writes nothing and says why, with the lines to write by hand only when it cannot write the index: a file it does not read gets what must hold and no line, a name of the trunk no line either. An error while it settles the names is said in the report and never leaves the merge in progress. On TypeORM the merge writes no name of the index: it cannot tell by the code whether two imports of one name are two entities or one. The index is left as the merge wrote it, as before, and each name the region of the imports gives more than once is said once, in the dry run as in the merge: `<index>: imports \`orders\` 2 times (from <file>, <file>); the kit writes no name on TypeORM after a merge: if they are distinct entities, import each but one under its own name and list that name in \`entities\`; if they are one entity, take out the extra import.` `init --force` says it the same way, and writes no name either. Nothing is said when no name is imported twice. On Drizzle, each text the settle of a merge writes in the index that the index did not hold before is recorded in a `Kit-Written:` trailer of the merge commit, and the lost-lines check never counts it as a line of the merge's own, so a line a careless resolution lost elsewhere in the index still stops the merge, as on main; every line the settle takes out is recorded in `Lost-Accepted:` by its file, its side and its text (`<file>@<side>#<hash>`), so it never accepts a loss of the other side at the same place. A `Lost-Accepted:` entry written as `file` or `file:line`, by a person or an earlier version, is read as before.

What the kit reads, on Drizzle. A module the index re-exports whole is the tables file of a context when it resolves to that file, whatever its name looks like; any other file of the project is read for what it is and keeps the names it exports, and a table of a context that bears one of them is listed under the name of its context. In a file it reads a declaration of one name (`export const orders = ...`, a function, a class, an enum, a type), a list (`export { orders }` of a name the file declares at its top level or imports by name), a name taken by name from any module (`export { held as orders } from './tables'`: from a file of the project it reads, what that file exports under it; from a package or a module it does not find, that name, a value unless written as a type), and the files of the project a file re-exports whole. What a file declares or takes by name wins over what a module it re-exports whole brings under the same name, as in the language. When something is not read with certainty and the index lacks a line for a name shared among what was read, the kit writes nothing and a note says what must hold, with no line to copy, `the kit wrote no name in it: ...`; an index without its region gets every line, the `export *` line of the context first. A command prints at most one such note, or the note of an index left as it stood. Nothing is printed when no name is shared among what was read, except when a name a tables file exports is written, as a word of the code, comments and strings left out, in a file of the project that is not read with certainty or in an `export` of the index that is not read: the note gives the line that names it apart.

`ddd-ts-kit init --force` settles a Drizzle index that holds both under one name and says what it settled; on TypeORM it writes no name, and says each name the index imports twice, as the merge does. `drizzle-generate` warns that a migration drops two tables an unsettled index lists under one name, `typeorm-generate` no longer takes the entity of one context for the entity of the same name of another when it warns of dropped tables, an entity imported under an alias through a file of its context or a barrel of it is read as listed, and `verify-slice` stages an index whose only changes are the statements that name the tables file of its context, the entries of what they import, and the line that lets the tables file of another context keep a name it holds and the slice came to share, an import written on several lines included; a line of the platform that only mentions a table of the context leaves the index out.

Limits. The kit resolves a module specifier by the aliases of `ddd-ts-kit.config.json` and relative paths, to a `.ts` file or the `index.ts` of a folder; it does not read `paths` of `tsconfig.json` beyond those aliases, `baseUrl`, nor the `package.json` of a folder, and where the compiler could read something else (a file and a folder of one name, a `.tsx`, a `.d.ts`, a `.js`, an `.mts` or a `.cts` beside or in place of the `.ts`, a folder that holds a `package.json`) the specifier resolves to nothing. On Drizzle a file is not read with certainty when it holds one of these, and while one stands the kit writes no name: two names declared in one statement, a pattern (`export const { orders } = tables`), a value exported (by `export const`, or a constant an export list names) that the file does not build itself, a re-export in disguise the kit cannot equate with what it names: it is the file's own only when it is a literal, an object, an array or a function written in place, or a call or a `new` whose arguments are not one binding alone (unless that binding is a constant of the file given a literal, as `pgSchema(MESSAGING_SCHEMA)`), or a binding or a member of one that the file declares, builds itself and does not export (the event store of the template, `eventStore.head`); any other value is not read: `export const kept = archived`, `const kept = tables.archived; export { kept }`, an alias of a table the file exports itself, a cast (`archived as typeof archived`), parentheses, a `!`, a condition, `same(archived)`, a name exported as a string (`export { kept as 'archived' }`), a `declare` of a value, a default export, a module exported as a name, a name with a character outside letters, digits, `_` and `$`, a regular expression literal or a template that does not close (a division is sometimes read as a regular expression), a `namespace` or `declare module` block, two modules re-exported whole that bring different things under one name, a package re-exported whole, or a module re-exported whole that resolves to nothing. What such a module re-exported whole holds is not looked into: a name it shares with another file through `export *` does not compile, as before, and one a line by name of the index already gives to something else stays hidden without a word. A tables file that is a symbolic link, or that a folder of its path that is a link leads to, is not read: the kit writes no name while one stands and gives it no note of a dropped table either; the note of the file not read says what must hold. That note comes when a name of another tables file is written, as a word, in the text the link points at within the project, as that text stands before the command: a name the same command writes through the link is said at the next command. A link that points outside the project, at another link or at nothing, or through a folder that is a link, is not looked into, as its reader tells it, and the note says it may export every name shared; a target written absolute is inside the project only when its path, as written, lies under the real path of the project, as git tells it. When a file the index re-exports is not read with certainty, the kit gives no line to write: it says which names may be shared and who keeps them. The note names what it does not read and why, the names it may export and the files that hold them, and what must hold: each table of that name needs a line by name in the index, the one that held the name before keeps it (in a merge, the one of the trunk, by its file when the trunk reads it, else as the index of the trunk exports it), each other one takes a name of its own; it is the same note in `generate`, `init --force` and `merge-trunk`, dry or real, and a `--continue` says it again only if it still holds. While a file the index re-exports, or the index itself, is not read with certainty, before the command or after it, the comparison of what the index gave before and after a command never leaves the index: the command exits as before, `0`, and writes what it wrote before. What the index exports after the command is said with that doubt while the index still names something not read after it, and plainly when it names none of it any more. It still says a table of a tables file the command writes again (the note of a table `generate --force` dropped). Each name it would have called lost gets one hedged sentence, `` the name `archived`, which 'src/legacy/tables.ts' gives the index, is exported by no line the kit can read after the command; it may still be exported through 'src/legacy/extra.ts' if it exports it`` (`one of them` for several), naming only what the index still names after the command; when it names none of it any more the loss is said plainly, still in a note, `` the name `archived`, which 'src/legacy/tables.ts' gave the index, is exported by no line after the command ('src/legacy/tables.ts', which the kit does not read with certainty, is no more named by the index)``; and each name moved another, `` `orders`, which named the `orders` of 'src/legacy/tables.ts', may name another table after the command (the kit does not read 'src/legacy/extra.ts')``, or plainly, `` `invoices`, which named the `invoices` of '<a>' by the lines the kit read, names the `invoices` of '<b>' after the command ('<gone>', which the kit does not read with certainty, is no more named by the index)``; a name two files read export different tables under, which the settle does not write while the file not read stands, is said by the note of the settle. A name lost or a name moved leaves the index as it stood, exit `3`, only when everything the index re-exports is read with certainty. Beside the names that file may export, the note says the names shared among what was read in a clause of their own (`orders` is shared by '<a>' and '<b>'; the kit writes no name while '<file>' stands), the keeper of each name on the trunk in a merge, and a name the index declares itself, which hides any table of that name. The kit compares the names the index exports as values, not the tables behind them, and no name it exports as a type only (`export type { ArchivedRow } from`), which `init --force` drops without a word when it stands outside the regions, as before, nor a default export the index re-exports (`export { default as archived } from '@/legacy/tables'`, `export { default } from`), dropped the same way, exit `0`: a table that stays exported under another name, through an alias the kit takes for a table of its own, still counts as a name lost, and the command says so and leaves the index. A table already hidden by a line a team wrote by hand, in favour of a file that is no tables file of a context, is not reported. On TypeORM the kit does not decide by the code whether two imports of one name bind one object, which no reading of the syntax settles (a re-export, an alias, a `new` that returns another object): a merge or `init --force` that leaves a name imported twice gets that name said, and the alias is written by hand, as before. On TypeORM the list of the entities is read as the names between the brackets of `entities`, comments left out: an entry is an entity when a name imported in the index bears it, and a spread or a constant built elsewhere is not followed. `init --force` keeps the lines outside the regions only by leaving the whole index as it stood, in the cases above; any other line written there goes with the rewrite, as before. A settle that `generate` refuses leaves the new tables out of the index until the lines of its note are written. On Drizzle, when the merged tree holds two tables files for a context that declare a name in common, no name of that merge is settled and no line rewritten; `init --force` afterwards gives a shared name to the context the index re-exports first, which may not be the trunk's. A table the index declares itself outside the regions (`export const legacyOrders = pgTable(...)`) is not in what `init --force` compares: it goes with the rewrite without a word, as before, and a name it held may then name the table of a context.

To move: nothing in a project that compiles and whose tables are all created. A project on Drizzle whose index names one table twice runs `ddd-ts-kit init --force` after a commit, which settles each name and says so, unless the note says the index was left as it stood, which says why, then `npm run db:generate <name>` to write the migration of the tables that were left out. A TypeORM project merged with a shared name gets the sentence and writes the alias by hand, as before (`import { orders as shippingOrders } from '...'`, and `shippingOrders,` in `entities`), then `npm run build && npm run db:generate migrations/<name>`. A project on Drizzle that stores an aggregate whose table bears a name the index declares, `Job` (`jobs`) or `Process` (`processes`), compiled on 0.112.0 and never created that table: it runs the same two commands. A script that reads the `Lost-Accepted:` trailers of merge commits now meets entries of the form `<file>@<side>#<hash>` beside `<file:line>` and `<file>`, and a new `Kit-Written:` trailer: it reads them as entries it does not know, or skips them; both come only from the settle of a Drizzle index.
