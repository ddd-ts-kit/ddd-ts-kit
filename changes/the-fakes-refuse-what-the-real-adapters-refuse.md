**The fake of a tenant-scoped aggregate is confined to its tenant, as the real repository is.** `InMemoryRepository` takes `{ confinedTo: scope }` as a second argument: a tenant finds, lists and counts what it saved only, a save under an id another tenant holds is refused with `ConcurrencyError`, an elevation widens reads and no write, and work that names no tenant is refused with `NoCurrentTenantError`. `generate repository` writes the fake of a tenant-scoped aggregate so, on the four ORM, with a scope that defaults to `oneTenantScope()` (new in `@ddd-ts-kit/testing`: the work of a member of `acme`), and the generated contract spec runs `tenantIsolationContract` on the fake and on the adapter, in place of the one case it held about the adapter. `tenantIsolationContract` takes `mutate` as an option, as `repositoryContract` does: without it the case of the update under a held id stays pending (#880).

To move: nothing is required, a fake already generated keeps working as a repository of no tenant. To confine the fake of a tenant-scoped aggregate, give its constructor `scope: ExecutionScope = oneTenantScope()`, pass `{ confinedTo: scope }` after the snapshots, and add `tenantIsolationContract(runner, { ...expectations, name: 'Fake<Aggregate>Repository', elevatedReads: true, createRepository: (scope) => new Fake<Aggregate>Repository(scope) })` to its contract spec; or run `generate repository <context> <Aggregate> --force` on committed files. A spec about a leak between tenants hands the fake the `executionScope` of its harness.

**The in-memory cache and event bus keep and hand values as the real ones do, as JSON carries them.** `InMemoryCache` keeps a copy at each write and hands a copy at each read; `InMemoryEventBus` delivers to the handlers of a type one copy of the event, and logs another in `published`. In both, a `Date` is its text, a class instance a plain object, and a value JSON cannot carry (a bigint, a cycle) is refused with a `TypeError`, at the write or at the publication. `cacheContract` gains two cases (a copy of its own, a value given back as JSON carries it) and `eventBusContract` one (an event received as JSON carries it, never the object that was published); the Redis cache with its default codec and the RabbitMQ, Kafka, NATS and Redis Streams buses serialise the same way (#880).

To move: a spec that read a `Date` or a class instance back from `InMemoryCache`, from a handler subscribed to `InMemoryEventBus` or from `published` / `publishedEvents()` now reads its JSON form, and one that compared a published event by identity (`toBe`, `toContain`) compares it by value (`toEqual`, `toContainEqual`): what it read before is what a broker or Redis never gave. A handler or a reader that needs an instant parses the text (`new Date(payload.at)`). A project that runs `cacheContract` on a `RedisCache` built with a `codec` that is not JSON leaves the contract to the default codec.

**The sequences and the data generator start again before each test, from a setup entry the generated runner configs list.** `@ddd-ts-kit/testing/setup/vitest` and `@ddd-ts-kit/testing/setup/jest` call the new `restartTestData()` before each test: every `sequence(...)` starts again at 1 and, where `@ddd-ts-kit/testing/faker` is in use, the data generator at its seed, so an id or a generated value no longer depends on the order of the tests of a file, nor on the files a worker ran before. `init` lists the entry in the unit, end-to-end and mutation configs of Vitest (`setupFiles`) and of Jest (`setupFilesAfterEnv`). `vitest` becomes an optional peer of `@ddd-ts-kit/testing`, imported from the Vitest entry only (#880).

To move: add `setupFiles: ['@ddd-ts-kit/testing/setup/vitest']` under `test` of `vitest.config.ts`, `vitest.e2e.config.ts` and `vitest.mutation.config.ts`, or `setupFilesAfterEnv: ['@ddd-ts-kit/testing/setup/jest']` to `jest.config.js`, `jest.e2e.config.js` and `jest.mutation.config.js`. A spec that expected an id drawn after those of an earlier test (`invoice-3` in the third test of a file) now reads the first of its own test (`invoice-1`); a `beforeEach(() => resetSequences())` of a spec can go.
