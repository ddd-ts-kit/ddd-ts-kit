**An aggregate shows a read-only `version` and `record`, and nothing else of what its store manages.** `AggregateRoot.version` was a public writable field and `pullEvents()` a public method that drains: an adapter, a mapper and a use case could all write the concurrency token or empty the events. The version an aggregate was loaded at and the events it has yet to announce now sit behind functions of `@ddd-ts-kit/kernel` that the infrastructure calls: `loadedAt(aggregate, version)`, `recordedEventsOf(aggregate)`, `takeRecordedEvents(aggregate)`, with `optimisticUpdate` and `appendChanges` moving the version themselves. They are keyed process-wide, so an aggregate built by another copy of the kernel is loaded, saved and followed the same, and what is no aggregate is refused with a `TypeError` instead of being stored as nothing. `EventSourcedAggregate` records in the same place: one list, no second one. The version is no longer an enumerable field: spreading, serialising or comparing an aggregate does not see it. `@ddd-ts-kit/testing` reads the events for a spec: `recordedBy(aggregate)` reads and leaves them, `withoutRecordedEvents(aggregate)` hands the aggregate with none, and `given(...).when(...)` no longer empties the aggregate it is given. `InMemoryRepository` saves through `optimisticUpdate` and loads through `loadedAt`, as a real adapter does. A generated mapper declares the two directions inside `aggregateMapper(...)` and never writes a version: `toDomain` answers the aggregate loaded at the version of its row.

A unit of work that rolls back puts the aggregates it saved back as it found them: at the version they were loaded at, with the events its saves had taken, ahead of what they recorded since. The same instance can be saved again; it used to keep the version of a row that no longer existed and to have lost its events, so a retry failed with a `ConcurrencyError` no writer had caused. `unitOfWorkContract` proves it on every ORM. `InMemoryUnitOfWork` undoes nothing, as before, and leaves the aggregates in step with what the fakes stored; a unit of work of your own that undoes nothing says so with `unitOfWorkOver(transaction, { rollsBack: false })`.

To move: `aggregate.version = row.version` no longer compiles (`TS2540`). In a generated mapper, wrap the object in `aggregateMapper({ toDomain, toRow })` of `@ddd-ts-kit/kernel` and let `toDomain` return `Aggregate.rehydrate(...)`: the repository adapter stays as it is. In an adapter that rebuilds the aggregate itself, `return loadedAt(Aggregate.rehydrate(row), row.version)`; each ORM package exports both functions too.
To move: `aggregate.pullEvents()` no longer compiles (`TS2339`): in a spec, `expect(recordedBy(aggregate)).toEqual([...])`; in a builder that discards the events of its arrangement, `return withoutRecordedEvents(built)`; in infrastructure of your own that dispatches, `takeRecordedEvents(aggregate)`.
To move: `domain-events/dispatched-on-save`, in `ddd-ts-kit check` and in `@ddd-ts-kit/eslint-plugin`, now reports a call of `takeRecordedEvents(...)` in `application/` or `infrastructure/` of a context, where it reported `.pullEvents()`.
To move: an in-memory repository generated with `--orm none` wrote the version itself: generate it again (`generate repository <context> <Aggregate> --force`), or save through `optimisticUpdate` and load through `loadedAt` as the new one does.
To move: `optimisticUpdate` takes an aggregate, not a `{ id, version }` object: a hand-written fake that saved a plain object passes its aggregate.
To move: code that read `version` from a spread or a JSON of an aggregate (`{ ...order }`) reads `order.version`.
