**Breaking: a unit of work run inside the one of another database dispatches its domain events before its own commit, and is built on `unitOfWorkOver`, which replaces `withinUnitOfWork`.** With two databases (a context on its own database, a second client), the inner unit of work opened and committed its own transaction while the events of what it saved waited for the end of the outer one: their `before-commit` handlers, the outbox append first, ran after that commit, outside any transaction of that database, and a failure there lost the event. Whether a `run` joins a transaction or opens one was decided twice, by the kernel on "a unit of work runs on this call chain" and by the adapter on "my transaction is open". It is now decided once: `unitOfWorkOver(transaction)` of `@ddd-ts-kit/kernel` answers a unit of work that keeps its own scope, calls `transaction` only to open one, and lets a nested `run` join the transaction and the scope of that unit of work, also when the `run` is made through the unit of work of another database. A new transaction is a new scope: its events are dispatched before its own commit, its `after-commit` handlers run after it. The units of work of `@ddd-ts-kit/knex` (the tenant-routed one included), `@ddd-ts-kit/drizzle`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/typeorm` and `InMemoryUnitOfWork` are built on it, and `unitOfWorkContract` of `@ddd-ts-kit/testing` proves it with two cases. `unitOfWorkMiddleware` no longer opens a scope of its own around the unit of work it is given: it calls `run`, and refuses before the handler a unit of work that opened no scope for the domain events (`UnscopedUnitOfWorkError`), where the events would leave at each save and the `after-commit` handlers run before the commit.

To move: in a `UnitOfWork` of your own, replace `withinUnitOfWork(work, (scoped) => ...)` by a unit of work built once, `private readonly unitOfWork = unitOfWorkOver((work) => this.database.transaction((transaction) => this.current.run(transaction, work)))`, and `run(work) { return this.unitOfWork.run(work); }`; drop the test that joined the open transaction, `transaction` is no longer called for a nested `run`. A unit of work written without the kernel and given to `unitOfWorkMiddleware`, to `kernelModule({ unitOfWork })` or as a fake in a test (`{ run: (work) => work() }`) is now refused with `UnscopedUnitOfWorkError`: build it the same way, or give `new InMemoryUnitOfWork()`.

**Breaking: a unit of work no longer commits once a nested `run` failed, also when the work caught the failure.** "A nested `run` joins the outer transaction: it commits or rolls back as a whole" held only while the failure travelled up. A handler that wrote `await unitOfWork.run(step).catch(fallback)`, or that caught the failure of a command it sent through the bus, kept what the step had written before it failed, and the domain events its saves had queued were dispatched. A `run` that joined and rejects now marks the unit of work, on the four ORM and in memory alike: the outermost `run` rejects with a `UnitOfWorkAbortedError` (`@ddd-ts-kit/kernel`) whose `cause` is the first such failure, before any event is dispatched, and the transaction rolls back. A failure that travels up rejects the outermost `run` as itself, as before. A unit of work of another database that failed and rolled back on its own aborts nothing. A retry (`retry` of `@ddd-ts-kit/aspects`, a loop) around a nested `run` or around a command sent from inside a unit of work no longer saves it: the second try may succeed, the unit of work still rolls back.

To move: where a handler catches the failure of a nested `unitOfWork.run` or of a command it sends, and goes on: check the condition before the write in place of catching after it, or let the failure through and catch it around the outermost `run` (the caller of the command), or move the step that may fail out of the unit of work (an `after-commit` handler that sends a command, an integration event). A retry belongs around the outermost `run`.

**`S3FileStorage.put` rejects with the failure of the service whatever the size of the content.** Above one part (8 MiB by default), a failure of the service (the network, a refused access, a missing bucket) was reported as `The operation was aborted`: the SDK destroys the stream that feeds a failed upload, and `put` preferred the failure of that stream. It now rejects with the failure of the upload, as it did for a content of one part; a content refused on its way (`FILE_TOO_LARGE`) still answers its refusal, and a source that fails still says why.

To move: nothing.

**Breaking: the read model of `@ddd-ts-kit/knex` is refused by name on a database that is not PostgreSQL.** It read as portable, beside an outbox and a processed-event store that do run on SQLite and MySQL, and it never was: on SQLite a `KnexReadModelStore` threw the raw `no such function: to_regclass` of the driver at its first write, and its rows alone answered `'stale'` to a later event (the stamp read back as a number) and read the trace of a deleted row as a live row. A `KnexReadModelStore` or a `KnexReadModelTable` built on a knex instance of another dialect now throws `The read model of @ddd-ts-kit/knex runs on PostgreSQL, and this knex speaks sqlite` when it is built; under database per tenant, where the database is known only inside a unit of work, at its first statement. The comments and the README no longer say "on every dialect".

To move: nothing on PostgreSQL. A test that builds a `KnexReadModelStore` on SQLite runs it on PGlite or on PostgreSQL, as the suites of the kit do, or gives the port its in-memory fake.

**Every `JobStore` answers a job already kept under the same id as a duplicate, and `jobStoreContract` holds them to it.** A second `add` of an id already kept raised the unique violation of the driver on `@ddd-ts-kit/knex` and `@ddd-ts-kit/drizzle`, which on PostgreSQL also ended the transaction of the command, answered `{ id, duplicate: false }` on `@ddd-ts-kit/typeorm`, `@ddd-ts-kit/prisma` and `@ddd-ts-kit/redis` although nothing was written, and replaced the first job in `InMemoryJobStore`. The six now add nothing, leave the first job as it was added and answer `{ id, duplicate: true }`, as they do for an idempotency key already kept; nothing is raised. `RedisJobStore.add` reads the id in Redis before it stages its write, as it read the idempotency key: inside a unit of work, with a server that is away, `add` now rejects in the command where a job without a key was reported lost after the commit (`onLostJob`).

To move: nothing for a project that enqueues through `JobQueue`, whose ids are generated. A `JobStore` of your own passes the new case of `jobStoreContract`: answer `{ id, duplicate: true }` for an id already kept, without writing.

**`TenantDatabases` leaves no rejection unhandled when an idle pool cannot be closed, and `S3FileStorage` no longer reads a missing bucket as an absent file.** Under database per tenant, an idle knex instance closed to make room for another tenant whose `destroy` rejected (a server that hung up) left a rejection nobody handled, which ends a Node.js process by default. The place is given to the next tenant all the same, and the new option `onCloseFailure(error, tenantId)` of `TenantDatabases` is told; without it the failure is dropped. `get` of `S3FileStorage` answered `undefined`, and `copy` and `move` `FILE_NOT_FOUND`, for any 404 of the service, `NoSuchBucket` included: a bucket that does not exist, a deployment to fix, read as "the file is absent". Only `NoSuchKey` and the `NotFound` of a head now do; any other answer is raised as it is. `stat` cannot tell: the service answers a head on a missing bucket as it answers a missing key.

To move: nothing.
